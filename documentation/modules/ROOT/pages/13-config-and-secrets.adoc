= Step 3 - Configuration and Secrets: One Image, Many Environments
include::_attributes.adoc[]

The legacy image had its greeting, environment name and API token baked in. That means one image per environment, and a credential that anyone with pull access can read. This step proves the token really can be read out of the image, then moves the settings to a ConfigMap and the token to a Secret. After this step, the *same image digest* can be promoted unchanged from test to production.

== Prerequisites

* xref:12-image-hygiene.adoc[Step 2] completed: `notes-app` is running and `$ROUTE` is set
* The `notes-legacy` ImageStream from xref:11-legacy-app.adoc[Step 1] still exists (for the first sub-step)

== How It Works

[cols="2,3,3",options="header"]
|===
| Kind of value | Where it lives | Example

| Environment-independent default
| The image (`ENV` in the Containerfile)
| `PORT=8080`

| Environment-specific, not sensitive
| ConfigMap, kept in Git
| `APP_ENV=workshop`, greeting, log level

| Sensitive
| Secret, created from a secret store and *never* committed to Git
| `API_TOKEN`
|===

== Steps to Apply

[#find-token]
=== 1. Find the token in the legacy image

*What:* Read the environment variables stored in the legacy image's metadata.

*Why:* Image layers and metadata are not encrypted. Every registry, mirror, cache, laptop and backup that holds the image also holds the token.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get istag notes-legacy:latest -n "$NS" --context {lab-context} \
  -o jsonpath='{range .image.dockerImageMetadata.Config.Env[*]}{@}{"\n"}\{end}' | grep -i token
----

.Verify: The token is visible in plain text
[%collapsible]
====
[.console-output]
[source,bash]
----
API_TOKEN=vendor-demo-token-8f3a9c21
----

Now try the same for the hardened image. It returns nothing:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get istag notes-app:latest -n "$NS" --context {lab-context} \
  -o jsonpath='{range .image.dockerImageMetadata.Config.Env[*]}{@}{"\n"}\{end}' | grep -i token
----

IMPORTANT: Deleting the `ENV` line in a later image version does not help. The old image, with the token, still exists in every registry and cache it was pushed to. A leaked credential must be *rotated*.
====

'''

[#configmap]
=== 2. Move settings to a ConfigMap

*What:* Create a ConfigMap with the greeting, environment name and log level.

*Why:* ConfigMaps are plain YAML, so they can live in Git next to the Deployment and be reviewed in a pull request, one per environment.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat 13-config-and-secrets/configmap.yaml
oc apply -f 13-config-and-secrets/configmap.yaml -n "$NS" --context {lab-context}
----

.Verify: The ConfigMap exists
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get configmap notes-app-config -n "$NS" --context {lab-context} -o jsonpath='{.data}' | jq
----

[.console-output]
[source,bash]
----
{
  "APP_ENV": "workshop",
  "APP_GREETING": "Hello from OpenShift",
  "LOG_LEVEL": "INFO"
}
----
====

'''

[#secret]
=== 3. Move the token to a Secret

*What:* Create the Secret imperatively from a literal value.

*Why:* There is deliberately no `secret.yaml` in this repository. A Secret manifest in Git is only base64-encoded, not encrypted. In a real environment, the value comes from your organisation's secret store.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc create secret generic notes-app-token \
  --from-literal=API_TOKEN="workshop-token-$(openssl rand -hex 4)" \
  -n "$NS" --context {lab-context}
----

.Verify: The Secret exists and its value is only base64-encoded
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get secret notes-app-token -n "$NS" --context {lab-context} -o jsonpath='{.data.API_TOKEN}' | base64 -d; echo
----

[.console-output]
[source,bash]
----
workshop-token-1a2b3c4d
----

Anyone with `get secret` permission in the namespace can do this. That is why RBAC on Secrets and the secret store integration (Session 3) matter.
====

'''

[#rollout-config]
=== 4. Roll out and verify

icon:clock[] ~20 seconds

*What:* Apply the Deployment that reads the ConfigMap with `envFrom` and the token with `secretKeyRef`.

*Why:* The image stays the same. Only the runtime configuration changes.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
diff -u 12-image-hygiene/deployment.yaml 13-config-and-secrets/deployment.yaml
oc apply -f 13-config-and-secrets/deployment.yaml -n "$NS" --context {lab-context}
oc rollout status deploy/notes-app -n "$NS" --context {lab-context}
----

.Verify: The app shows the injected settings
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl -sk "https://$ROUTE/api/info" | jq '{greeting, environment, api_token}'
----

[.console-output]
[source,bash]
----
{
  "greeting": "Hello from OpenShift",
  "environment": "workshop",
  "api_token": "configured (ends with ...3c4d)"
}
----

NOTE: If `jq` reports a parse error, or you see an HTML "Application is not available" page right after a rollout, wait a few seconds and try again. This Deployment has no readiness probe yet, so the router can send traffic to the new pod before the app is listening. xref:14-health-and-resources.adoc[Step 4] fixes exactly this.
====

'''

[#change-config]
=== 5. Change a setting without rebuilding

*What:* Change the greeting in the ConfigMap and restart the Deployment.

*Why:* Shows the operational benefit: a configuration change takes seconds and does not need a new image, a new scan or a new approval of the image.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc patch configmap notes-app-config -n "$NS" --context {lab-context} \
  --type merge -p '{"data":{"APP_GREETING":"Hello, configured at runtime"}}'
oc rollout restart deploy/notes-app -n "$NS" --context {lab-context}
oc rollout status deploy/notes-app -n "$NS" --context {lab-context}
----

NOTE: Environment variables are read when the container starts, so a ConfigMap change needs a restart. In Session 3, Kustomize's `configMapGenerator` adds a content hash to the ConfigMap name, so every change triggers a rollout automatically through GitOps.

.Verify: New greeting, same image digest
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl -sk "https://$ROUTE/api/info" | jq -r .greeting
oc get deploy notes-app -n "$NS" --context {lab-context} -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
----

[.console-output]
[source,bash]
----
Hello, configured at runtime
image-registry.openshift-image-registry.svc:5000/app-lifecycle/notes-app@sha256:4b1c...
----

The digest is the same one you saw in xref:12-image-hygiene.adoc#provenance[Step 2].
====

'''

== What This Solves (Compared to Step 2)

[cols="2,3",options="header"]
|===
| Problem from Step 2 | How This Step Solves It

| No way to configure the app per environment
| ConfigMap per environment, same image everywhere

| Token baked into the image (Step 1)
| Secret injected at runtime, absent from the image

| Configuration changes need a rebuild
| Change the ConfigMap and restart
|===

== What This Does NOT Solve (Yet)

[cols="2,3",options="header"]
|===
| Remaining Problem | Addressed In

| The Secret value was typed by hand
| Session 3: secret store integration (for example the External Secrets Operator) as part of GitOps

| No health checks: a broken pod still receives traffic
| xref:14-health-and-resources.adoc[Step 4: Health and Resources]
|===

== Alternatives Considered

[cols="2,4",options="header"]
|===
| Approach | Notes

| ConfigMap and Secret as environment variables (this workshop)
| Simple, works with almost every application. Requires a restart to pick up changes.

| ConfigMap and Secret mounted as files
| Updated in the running pod without a restart, if the application re-reads the file. Better for certificates and large config files.

| Secret store integration (External Secrets Operator, Secrets Store CSI driver)
| The value lives only in the secret store and is synchronised into the cluster. Recommended for production; covered in Session 3.

| Sealed or encrypted Secrets in Git
| Keeps everything in Git, but key management moves to the cluster. Useful when no central secret store is available.
|===

== Reset

Revert the Deployment to its Step 2 version first so no pod references the objects you delete next.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----

oc delete secret notes-app-token -n "$NS" --context {lab-context} --ignore-not-found
oc delete -f 13-config-and-secrets/configmap.yaml -n "$NS" --context {lab-context} --ignore-not-found
----

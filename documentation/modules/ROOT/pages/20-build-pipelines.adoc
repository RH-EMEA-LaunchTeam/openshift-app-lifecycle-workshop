= Session 2 - Build Pipelines: From Source to an Approved Image
include::_attributes.adoc[]

In Session 1 you built images by hand with `oc start-build` and judged them against the admission checklist by reading YAML. This session turns the build into a pipeline that runs the same way every time, for every team: *applications you build from source* are cloned, built, scanned, and promoted only if the scan passes.

xref:30-vendor-intake.adoc[Session 3] continues with the same pipelines: Git triggers, an *intake* pipeline for images you cannot rebuild, and pipelines that the platform team publishes once for every tenant.

The pipelines run on *OpenShift Pipelines*, Red Hat's supported distribution of the Tekton project, and scan with *Red Hat Advanced Cluster Security (ACS)*. If your teams already use another CI system, the same stages and gates apply. Only the tool changes.

== Before you start

This session runs on a fresh cluster that several participants share. Each participant has their own user and their own namespace, with admin rights on that namespace only, like a real tenant. The instructor has already done the platform-side setup.

[cols="2,4",options="header"]
|===
| Prepared by the platform team (instructor) | Why it is not part of your steps

| OpenShift Pipelines operator
| Cluster-wide component, installed once by the platform team

| ACS Central and SecuredCluster, plus an `acs-api` Secret in your namespace
| The security team owns the scanner and hands each tenant a token for its CI

| LimitRange and ResourceQuota on your namespace
| Platform guardrails from xref:14-health-and-resources.adoc#tenant-guardrails[Session 1, Step 4]

| `platform-pipelines` namespace with shared Tasks and Pipelines
| Used in xref:30-vendor-intake.adoc[Session 3]
|===

NOTE: To prepare your own cluster, run `20-session-prep/platform-setup.sh` as cluster-admin, *at least one hour before the session*. Its header explains the arguments. Most of the time goes into the first download of the ACS vulnerability database (about 40 minutes on a fresh cluster); the script waits until a real scan succeeds.

=== 1. Complete the setup page

*What:* Follow xref:00-setup.adoc[Cluster Setup] with your own user and namespace, including the Session 2 variables.

*Why:* Every command in this session uses `$NS`, `$GIT_REPO_URL` and the `{lab-context}` context.

.Verify: Context, namespace and tools
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc whoami --context {lab-context}
oc get project "$NS" --context {lab-context} -o name
tkn version --component client
----

[.console-output]
[source,bash]
----
user1
project.project.openshift.io/app-lifecycle-user1
Client version: 0.46.2
----

Any recent `tkn` works.

If `tkn` is missing on your workstation, install it from the web console (*?* > *Command line tools*), or use the Web Terminal as described in the xref:00-setup.adoc#prerequisites[setup TIP].
====

'''

[#catch-up]
=== 2. Catch up to the end of Session 1

icon:clock[] ~2 minutes

*What:* Run the catch-up script. It builds both images and deploys `notes-app` in the state it had at the end of xref:15-stateless-and-scale.adoc[Session 1, Step 5].

*Why:* This is a new cluster, so nothing from Session 1 exists yet. The script needs only admin rights on your namespace. The platform team has already put the legacy image into your namespace, so only the hardened image is built.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
./20-session-prep/catch-up.sh "$NS" {lab-context}
----

Then export the route and save it in `myenv.sh`:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
export ROUTE=$(oc get route notes-app -n "$NS" --context {lab-context} -o jsonpath='{.spec.host}')
echo "export ROUTE=$ROUTE" >> myenv.sh
----

NOTE: The script is safe to re-run. If the legacy image was not provided by the platform team, the script builds it too, pulling its base from Docker Hub. If that stops with `toomanyrequests`, wait a few minutes and run it again.

.Verify: notes-app answers with version 1.0
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl -sk "https://$ROUTE/api/info" | jq '{version, storage}'
oc get istag -n "$NS" --context {lab-context}
----

[.console-output]
[source,bash]
----
{
  "version": "1.0",
  "storage": "postgresql"
}
NAME                  IMAGE REFERENCE                                                                       UPDATED
notes-app:latest      image-registry.openshift-image-registry.svc:5000/app-lifecycle-user1/notes-app@sha256:...      About a minute ago
notes-legacy:latest   image-registry.openshift-image-registry.svc:5000/app-lifecycle-user1/notes-legacy@sha256:...   3 minutes ago
----

Version `1.0` comes from the hand-started build. After Step 2 the version is a Git commit.
====

'''

== Questions to prepare

* Which registry will be the long-term source of truth for images, and how does it relate to the cluster's internal registry?
* Who owns the pipeline definitions: the platform team, the tenants, or both (central templates, tenant-specific parameters)?
* Which vulnerabilities should block a build, and who decides?

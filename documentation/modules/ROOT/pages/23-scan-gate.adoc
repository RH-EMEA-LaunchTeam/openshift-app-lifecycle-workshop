= Step 3 - Scan Gate: Vulnerable Images Never Reach the Deployment
include::_attributes.adoc[]

The pipeline from Step 2 promotes any image that builds. This step adds a vulnerability scan between build and promote. The image is still built and pushed, so the security team can analyse it, but an image with *fixable critical* vulnerabilities is never promoted to `notes-app:latest`, and therefore never rolled out.

Critical vulnerabilities that do not have a fix yet are reported but do not block. Rebuilding cannot remove them, so blocking on them would stop every build of every team until the vendor of the base image ships a fix. Deciding what to do about them is a risk decision for the security owner, not a build failure. This is also how the default ACS policies treat severity.

You will run the pipeline twice: once with the UBI-based `Containerfile` (passes), and once with the legacy Containerfile from Session 1, which uses a Docker Hub base image (blocked).

== Prerequisites

* xref:22-source-pipeline.adoc[Step 2] completed: `notes-app-build` exists and has run at least once
* The `acs-api` Secret exists in your namespace (created by the platform team)

== How It Works

[source,text]
----
 clone  -->  build  -->  scan (ACS)  -- PASS -->  promote  -->  rollout
                             |
                             +-- FAIL --> pipeline stops; notes-app:latest unchanged
----

The `acs-image-scan` Task downloads `roxctl` from ACS Central, so the client always matches the server version, asks Central to scan the image *by digest*, and splits the critical CVEs into *fixable* and *no fix yet*. It authenticates with an API token that has the *Continuous Integration* role. The token comes from the `acs-api` Secret, which the platform team provides to each tenant, so the token never appears in a pipeline definition or in Git.

[cols="2,3",options="header"]
|===
| Parameter | Effect

| `fail-on-critical: "true"` (default)
| Fixable critical CVEs fail the Task, so `promote` never runs

| `fail-on-critical: "false"`
| The scan reports and records a verdict, but does not stop the pipeline. Used in xref:30-vendor-intake.adoc[Session 3], where a separate gate decides.
|===

=== 1. Look at the scan Task and its credentials

*Why:* The security team owns the scanner and its policies. Tenants get a narrowly scoped token, not access to the ACS console.

== What This Solves (Compared to Step 2)

[cols="2,3",options="header"]
|===
| Step 2 | Now

| Every image that builds is promoted
| Images with fixable critical CVEs stop before promotion; unfixed ones are reported

| Vulnerabilities found after deployment, if ever
| Found at build time, with the CVE list in the pipeline log

| The scanner is someone else's tool
| Every tenant pipeline uses the security team's scanner through a scoped token
|===

== What This Does NOT Solve (Yet)

[cols="2,3",options="header"]
|===
| Remaining Problem | Addressed In

| Someone still starts the pipeline by hand
| xref:30-vendor-intake.adoc[Session 3]: Pipelines as Code

| Images we cannot rebuild from source
| xref:30-vendor-intake.adoc[Session 3]: Vendor Image Intake

| CVEs published *after* the image passed the gate
| Session 7 (monthly patch cycle) and Session 8 (ACS in daily operations)

| The rule "no fixable critical CVEs" is hard-coded in the pipeline
| Session 8: `roxctl image check` evaluates policies that the security team manages centrally in ACS, so the rule changes without editing any pipeline
|===

== Alternatives Considered

[cols="2,4",options="header"]
|===
| Approach | Notes

| `roxctl image scan` with a severity and fixability threshold (this step)
| Simple and explicit. The threshold lives in the pipeline.

| Block on every critical CVE, fixed or not
| Strictest, but blocks builds for vulnerabilities nobody can fix yet, which pushes teams to bypass the gate.

| `roxctl image check` against ACS policies
| The production pattern: the security team enables build-time enforcement on policies in ACS, and every pipeline obeys them. Covered in Session 8.

| Admission control (ACS admission controller, or signature verification)
| Blocks non-compliant images at deploy time, whatever their source. Complements a pipeline gate and does not replace it, because it gives feedback much later.
|===

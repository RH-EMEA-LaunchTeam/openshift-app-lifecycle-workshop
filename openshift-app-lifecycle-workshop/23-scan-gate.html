OpenShift Application Lifecycle Workshop

The pipeline from Step 2 promotes any image that builds. This step adds a vulnerability scan between build and promote. The image is still built and pushed, so the security team can analyse it, but an image with critical vulnerabilities is never promoted to notes-app:latest, and therefore never rolled out.

You will run the pipeline twice: once with the UBI-based Containerfile (passes), and once with the legacy Containerfile from Session 1, which uses a Docker Hub base image (blocked).

Prerequisites

  • Step 2 completed: notes-app-build exists and has run at least once

  • The acs-api Secret exists in your namespace (created by the platform team)

How It Works

 clone  -->  build  -->  scan (ACS)  -- PASS -->  promote  -->  rollout
                             |
                             +-- FAIL --> pipeline stops; notes-app:latest unchanged

The acs-image-scan Task downloads roxctl from ACS Central, so the client always matches the server version, and asks Central to scan the image by digest. It authenticates with an API token that has the Continuous Integration role. The token comes from the acs-api Secret, which the platform team provides to each tenant, so the token never appears in a pipeline definition or in Git.

Parameter Effect

fail-on-critical: "true" (default)

Critical CVEs fail the Task, so promote never runs

fail-on-critical: "false"

The scan reports and records a verdict, but does not stop the pipeline. Used in Step 5, where a separate gate decides.

Steps to Apply

1. Look at the scan Task and its credentials

What: Check that the acs-api Secret exists, without printing its value, and read the scan Task.

Why: The security team owns the scanner and its policies. Tenants get a narrowly scoped token, not access to the ACS console.

oc get secret acs-api -n "$NS" --context lab -o jsonpath='{.data}' | jq 'keys'
cat 23-scan-gate/acs-scan-task.yaml
Verify: Endpoint and token keys exist 
[
  "ROX_API_TOKEN",
  "ROX_ENDPOINT"
]

2. Add the scan to the pipeline

What: Create the scan Task and update notes-app-build to version 2, which runs scan between build and promote.

Why: The gate sits before promotion. The pipeline does not need to know anything about deployments: if notes-app:latest does not move, nothing rolls out.

diff 22-source-pipeline/pipeline.yaml 23-scan-gate/pipeline.yaml
oc apply -f 23-scan-gate/acs-scan-task.yaml -f 23-scan-gate/pipeline.yaml \
  -n "$NS" --context lab
Verify: The pipeline has four Tasks 
oc get pipeline notes-app-build -n "$NS" --context lab -o jsonpath='{.spec.tasks[*].name}{"\n"}'
clone build scan promote

3. Run it on the UBI-based image

~3 minutes

What: Run the pipeline exactly as in Step 2.

Why: The hardened image is built on a Red Hat Universal Base Image, which Red Hat patches and rebuilds regularly. It is expected to pass.

envsubst < 23-scan-gate/pipelinerun.yaml | oc create -f - -n "$NS" --context lab
tkn pipelinerun logs --last -f -n "$NS" --context lab
Verify: Scan passed, image promoted

In the scan Task log:

[scan : scan] Scanning image-registry.openshift-image-registry.svc:5000/.../notes-app@sha256:... for CRITICAL vulnerabilities...
[scan : scan] verdict: PASS
tkn pipelinerun list -n "$NS" --context lab | head -2
NAME                    STARTED         DURATION   STATUS
notes-app-build-p8x2m   3 minutes ago   2m40s      Succeeded
A UBI image can occasionally have a critical CVE for a few days, between the fix being published and the base image being rebuilt. If that happens here, the gate is doing its job. Session 6 covers how the monthly patch cycle handles it.

4. Run it on the legacy image

~3 minutes

What: Run the same pipeline, but build from app/Containerfile.legacy (Docker Hub base image).

Why: Same code, same pipeline, different base image. This shows the base image is the biggest single source of vulnerabilities, and shows the gate stopping a bad image.

VERSION_BEFORE=$(curl -sk "https://$ROUTE/api/info" | jq -r .version)
envsubst < 23-scan-gate/pipelinerun-legacy.yaml | oc create -f - -n "$NS" --context lab
tkn pipelinerun logs --last -f -n "$NS" --context lab
Verify: The scan failed and nothing was promoted

The scan Task prints a table of critical CVEs from the Debian-based image and ends with:

[scan : scan] verdict: FAIL
[scan : scan] Critical vulnerabilities found: the image is NOT promoted.
tkn pipelinerun list -n "$NS" --context lab | head -2
echo "before: $VERSION_BEFORE"
echo "now:    $(curl -sk "https://$ROUTE/api/info" | jq -r .version)"
NAME                           STARTED         DURATION   STATUS
notes-app-build-legacy-t5v7c   3 minutes ago   2m50s      Failed
before: 3f2c1ab9e8...
now:    3f2c1ab9e8...

The pipeline failed at scan, promote was never started, and the running application did not change. The legacy image is still in the registry under its commit tag, so the security team can look at it, but no Deployment uses it.

What This Solves (Compared to Step 2)

Step 2 Now

Every image that builds is promoted

Images with critical CVEs stop before promotion

Vulnerabilities found after deployment, if ever

Found at build time, with the CVE list in the pipeline log

The scanner is someone else’s tool

Every tenant pipeline uses the security team’s scanner through a scoped token

Alternatives Considered

Approach Notes

roxctl image scan with a severity threshold (this step)

Simple and explicit. The threshold lives in the pipeline.

roxctl image check against ACS policies

The production pattern: the security team enables build-time enforcement on policies in ACS, and every pipeline obeys them. Covered in Session 7.

Admission control (ACS admission controller, or signature verification)

Blocks non-compliant images at deploy time, whatever their source. Complements a pipeline gate and does not replace it, because it gives feedback much later.

Reset

The pipeline stays at version 2 for the next steps. To go back to version 1:

oc apply -f 22-source-pipeline/pipeline.yaml -n "$NS" --context lab
oc delete -f 23-scan-gate/acs-scan-task.yaml -n "$NS" --context lab --ignore-not-found

OpenShift Application Lifecycle Workshop

On a VM, the application has the whole machine to itself and somebody notices when it hangs. On a shared platform, the scheduler has to know how much CPU and memory each pod needs, and the platform has to know whether each pod is alive and ready for traffic. This step adds both, from two sides: the platform team sets guardrails on the namespace (LimitRange and ResourceQuota), and the application declares its own requests, limits and health probes.

Prerequisites

  • Step 3 completed: notes-app runs with its ConfigMap and Secret

  • $ROUTE set

How It Works

Object Owner Purpose

ResourceQuota

Platform team

Caps the total CPU, memory, storage and pod count for the whole namespace

LimitRange

Platform team

Gives containers default requests and limits if they declare none, and enforces a maximum

Requests and limits

Application

Requests: what the scheduler reserves. Memory limit: the pod is killed (OOMKilled) above it.

Startup probe

Application

Gives slow-starting apps time before liveness checks begin

Liveness probe

Application

"Is the process stuck?" Fails: the container is restarted.

Readiness probe

Application

"Can I take traffic right now?" Fails: the pod is removed from the Service, but not restarted.

notes-app exposes /healthz/live (always OK while the process runs) and /healthz/ready (OK only when its storage is writable or reachable).

Steps to Apply

1. Apply the platform guardrails

What: Apply a LimitRange and a ResourceQuota to the namespace.

Why: These belong to the platform team, not the application. In Session 3 they are part of the namespace template that every tenant gets through a pull request.

oc apply -f 14-health-and-resources/limitrange.yaml -f 14-health-and-resources/resourcequota.yaml \
  -n "$NS" --context lab
Verify: Quota usage is tracked 
oc describe resourcequota tenant-quota -n "$NS" --context lab
Name:                   tenant-quota
Namespace:              app-lifecycle
Resource                Used  Hard
--------                ----  ----
limits.memory           0     8Gi
persistentvolumeclaims  0     5
pods                    1     20
requests.cpu            0     2
requests.memory         0     4Gi
requests.storage        0     20Gi

The running pod was created before the quota existed, so it uses no requests yet. The numbers update as soon as the pod is replaced in the next sub-step.

2. Add probes and resources to the Deployment

~20 seconds

What: Apply the Deployment with requests, a memory limit, startup, liveness and readiness probes and a termination grace period.

Why: Without requests the scheduler cannot place pods sensibly. Without probes, a hung or not-yet-ready pod still receives traffic.

diff -u 13-config-and-secrets/deployment.yaml 14-health-and-resources/deployment.yaml
oc apply -f 14-health-and-resources/deployment.yaml -n "$NS" --context lab
oc rollout status deploy/notes-app -n "$NS" --context lab
There is no CPU limit on purpose. A CPU limit throttles the app even when the node has idle CPU. A memory limit is still important because memory cannot be throttled, only reclaimed by killing the process.
Verify: Probes are configured and passing 
oc describe pod -l app.kubernetes.io/name=notes-app -n "$NS" --context lab | grep -E 'Liveness|Readiness|Startup|Requests|Limits' -A2 | head -20
oc describe resourcequota tenant-quota -n "$NS" --context lab | grep -E 'requests|limits'
    Limits:
      memory:  256Mi
    Requests:
      cpu:      50m
      memory:   128Mi
    Liveness:   http-get http://:http/healthz/live delay=0s timeout=1s period=10s #success=1 #failure=3
    Readiness:  http-get http://:http/healthz/ready delay=0s timeout=1s period=5s #success=1 #failure=2
    Startup:    http-get http://:http/healthz/live delay=0s timeout=1s period=2s #success=1 #failure=30
limits.memory           256Mi  8Gi
requests.cpu            50m    2
requests.memory         128Mi  4Gi

3. Break readiness on purpose

~15 seconds (two failed readiness checks, 5 seconds apart)

What: Make the app’s data file read-only inside the running container, watch the pod become not ready, then fix it.

Why: This shows the difference between readiness and liveness in practice: the pod stops receiving traffic but is not restarted, so it can recover on its own.

oc exec deploy/notes-app -n "$NS" --context lab -- chmod a-w /opt/app-root/data/notes.txt
sleep 15
oc get pods -l app.kubernetes.io/name=notes-app -n "$NS" --context lab
curl -sk -o /dev/null -w '%{http_code}\n' "https://$ROUTE/"
NAME                         READY   STATUS    RESTARTS   AGE
notes-app-5f7d9c8b6d-k8w2n   0/1     Running   0          2m
503

Now repair it:

oc exec deploy/notes-app -n "$NS" --context lab -- chmod u+w /opt/app-root/data/notes.txt
sleep 10
oc get pods -l app.kubernetes.io/name=notes-app -n "$NS" --context lab
Verify: The pod recovered without a restart 
NAME                         READY   STATUS    RESTARTS   AGE
notes-app-5f7d9c8b6d-k8w2n   1/1     Running   0          2m30s

RESTARTS is still 0. With a single replica, the whole app was unavailable while the pod was not ready. Step 5 fixes that with more replicas.

oc get events -n "$NS" --context lab --field-selector reason=Unhealthy | tail -3

4. See the defaults in action

What: Start a pod that declares no resources at all and check what it received.

Why: Vendors often ship manifests without resources. The LimitRange makes sure those pods still get sensible values and still count against the quota.

oc run no-resources --image=registry.access.redhat.com/ubi9/ubi-minimal \
  -n "$NS" --context lab --command -- sleep 3600
oc get pod no-resources -n "$NS" --context lab -o jsonpath='{.spec.containers[0].resources}' | jq
oc run prints a Warning: would violate PodSecurity "restricted:latest" message. It is only a warning: the request does not set the security fields itself, and the restricted-v2 SCC adds them when the pod is admitted. Pods from a proper Deployment manifest would normally set them explicitly.
Verify: The LimitRange filled in the gaps 
{
  "limits": {
    "memory": "1Gi"
  },
  "requests": {
    "cpu": "50m",
    "memory": "128Mi"
  }
}

Clean up the test pod:

oc delete pod no-resources -n "$NS" --context lab --ignore-not-found

What This Solves (Compared to Step 3)

Problem from Step 3 How This Step Solves It

Broken pods still receive traffic

Readiness probe removes them from the Service

Hung processes stay hung

Liveness probe restarts them

The scheduler does not know what the app needs

Requests and memory limit

One tenant can starve the cluster

ResourceQuota and LimitRange on the namespace

Alternatives Considered

Approach Notes

Requests plus memory limit, no CPU limit (this workshop)

Good default for most web workloads: predictable scheduling, no CPU throttling.

Requests equal to limits (Guaranteed QoS)

Most predictable, least efficient. Useful for latency-sensitive or licensed workloads.

No requests at all

Pods become BestEffort and are the first to be evicted under pressure. Not acceptable on a shared platform; the LimitRange prevents it.

Reset

Revert the Deployment first, then remove the guardrails (the quota last, so nothing gets created without limits in between).

oc delete pod no-resources -n "$NS" --context lab --ignore-not-found
oc apply -f 13-config-and-secrets/deployment.yaml -n "$NS" --context lab
oc delete -f 14-health-and-resources/limitrange.yaml -n "$NS" --context lab --ignore-not-found
oc delete -f 14-health-and-resources/resourcequota.yaml -n "$NS" --context lab --ignore-not-found

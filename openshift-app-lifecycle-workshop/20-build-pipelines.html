OpenShift Application Lifecycle Workshop

In Session 1 you built images by hand with oc start-build and judged them against the admission checklist by reading YAML. This session turns both into pipelines that run the same way every time, for every team:

  • Applications you build from source go through a pipeline: clone, build, scan, and promote only if the scan passes.

  • Images you cannot rebuild, usually delivered by a vendor, go through an intake pipeline: inspect, scan, test under the platform’s default security, then approve, fix or reject.

On most platforms that host vendor software, the second pipeline matters more. This session gives it the most time.

The pipelines run on OpenShift Pipelines, Red Hat’s supported distribution of the Tekton project, and scan with Red Hat Advanced Cluster Security (ACS). If your teams already use another CI system, the same stages and gates apply. Only the tool changes.

Before you start

This session runs on a fresh cluster that several participants share. Each participant has their own user and their own namespace, with admin rights on that namespace only, like a real tenant. The instructor has already done the platform-side setup.

To prepare your own cluster, run 20-session-prep/platform-setup.sh as cluster-admin. Its header explains the arguments.

1. Complete the setup page

What: Follow Cluster Setup with your own user and namespace, including the Session 2 variables.

Why: Every command in this session uses $NS, $GIT_REPO_URL and the lab context. Step 4 also needs $GITHUB_FORK_URL and $PAC_WEBHOOK_URL.

Verify: Context, namespace and tools 
oc whoami --context lab
oc get project "$NS" --context lab -o name
tkn version --component client
user1
project.project.openshift.io/app-lifecycle-user1
Client version: 0.4x.x

If tkn is missing, use the OpenShift Web Terminal, which includes it.

2. Catch up to the end of Session 1

~3 minutes

What: Run the catch-up script. It builds both images and deploys notes-app in the state it had at the end of Session 1, Step 5.

Why: This is a new cluster, so nothing from Session 1 exists yet. The script needs only admin rights on your namespace.

./20-session-prep/catch-up.sh "$NS" lab

Then export the route and save it in myenv.sh:

export ROUTE=$(oc get route notes-app -n "$NS" --context lab -o jsonpath='{.spec.host}')
echo "export ROUTE=$ROUTE" >> myenv.sh
The legacy image pulls its base from Docker Hub. If the script stops with toomanyrequests, wait a few minutes and run it again. It is safe to re-run.
Verify: notes-app answers with version 1.0 
curl -sk "https://$ROUTE/api/info" | jq '{version, storage}'
oc get istag -n "$NS" --context lab
{
  "version": "1.0",
  "storage": "postgresql"
}
NAME                  IMAGE REFERENCE                                   UPDATED
notes-app:latest      image-registry.openshift-image-registry.svc:5000/...   1 minute ago
notes-legacy:latest   image-registry.openshift-image-registry.svc:5000/...   1 minute ago

Version 1.0 comes from the hand-started build. After Step 2 the version is a Git commit.

Questions to prepare

  • Which registry will be the long-term source of truth for images, and how does it relate to the cluster’s internal registry?

  • Do vendors deliver source, Containerfiles, images or image archives? For how many of your applications each?

  • Who owns the pipeline definitions: the platform team, the tenants, or both (central templates, tenant-specific parameters)?

  • Who may accept a vulnerability risk for a vendor image, and for how long?
